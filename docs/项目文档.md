## 一、系统需求分析

### 1.1 项目背景

航空票务系统的核心任务，是在航班资源有限的情况下，支持用户完成航班查询、购票、支付、退票和改签等操作，同时支持管理员维护航班、机场、航司、机型、票价和航班实例等基础数据。

本项目面向国内航线场景，设计并实现一个简化版航空票务管理数据库系统，围绕库存扣减、订单状态流转、退改签费用计算和中转查询等数据库密集场景展开，包括：

- 用户端的航班查询、临近机场或中转低价方案推荐、订单创建与查询、模拟支付、退票和改签；
- 管理端的城市、机场、航司、机型、航班计划、航班实例和舱位定价维护；
- 数据库层面的库存一致性、订单状态管理、客票状态管理和退改记录保存。

### 1.2 系统目标

本系统需要完成以下目标：

1. 支持完整购票流程：用户可以注册登录，按出发城市、到达城市和出行日期查询航班，选择合适的航班实例和舱位后下单，并完成模拟支付。
2. 支持订单和客票管理：系统需要记录订单、客票、乘机人、票价快照等信息，使用户能够查看自己的订单详情和客票状态。
3. 支持退票和改签流程：用户可以对未起飞且仍有效的客票发起退票或改签。系统需要根据距离起飞时间计算手续费，并在退改过程中同步更新客票状态、订单状态和库存。
4. 支持管理员维护基础数据：管理员可以维护城市、机场、临近机场、航空公司、机型、航班计划、航班实例和舱位定价等数据，为前台查询和购票提供数据基础。
5. 保证票务库存一致性：下单、退票、改签和订单超时取消都会影响库存。系统需要避免同一张票被重复售卖，避免库存扣减和回补出现不一致。
6. 支持多种航班推荐方式：在直飞航班之外，系统还需要支持单次中转方案和临近机场替代方案，以覆盖更多实际出行场景。

### 1.3 用户角色分析

系统主要面向两类角色：普通用户和管理员。普通用户负责完成航班查询、购票、支付、订单查询、退票和改签等前台业务；管理员负责维护系统运行所需的基础数据，并对订单数据进行运营核对。两类角色使用不同入口登录，系统根据登录身份限制其可访问的功能范围。

| 角色     | 主要需求                                                     | 权限边界                                                     |
| -------- | ------------------------------------------------------------ | ------------------------------------------------------------ |
| 普通用户 | 注册登录、维护个人信息和乘机人信息、查询航班、创建订单、完成支付、查询订单、申请退票或改签 | 只能查看和操作本人数据，不能访问其他用户订单，也不能修改航班、机场、票价等基础数据 |
| 管理员   | 登录管理端，维护城市、机场、临近机场、航空公司、机型、航班计划、航班实例和舱位定价等基础数据，查看订单数据用于运营核对 | 可以维护基础数据，可以只读查看订单数据，但不参与普通用户的下单、支付、退票和改签流程 |

### 1.4 功能需求分析

根据航空票务业务流程，系统功能划分为六个模块：用户与权限管理、基础数据维护、航班查询、订单与购票、退票改签、中转与临近机场推荐。实际实现覆盖基础数据维护、航班搜索、下单支付、超时释放、退票改签和订单查询。

| 功能模块           | 需求说明                                                     |
| ------------------ | ------------------------------------------------------------ |
| 用户与权限管理     | 系统需要支持普通用户注册、普通用户登录、管理员登录和退出登录。普通用户注册时需要填写手机号、密码和昵称，手机号保持唯一，密码不得明文存储。登录后，系统根据用户身份区分普通用户端和管理端权限，保证普通用户只能操作自己的订单、客票和乘机人数据。 |
| 基础数据维护       | 系统需要支持管理员维护城市、机场、临近机场关系、航空公司、机型、航班计划、航班飞行日、航班经停、航班实例和舱位定价等基础数据。其中，航班计划表示固定航线安排，航班实例表示某个具体日期执行的航班，舱位定价表示某个航班实例下不同舱位和票价类型的价格与余票。 |
| 航班查询           | 用户可以按照出发城市、到达城市和出行日期查询航班。系统需要返回直飞航班、中转航班和临近机场方案，并展示航班号、航司、起降机场、起降时间、舱位、价格、余票和方案类型。系统还需要支持按价格、起飞时间、航司和舱位等条件进行筛选或排序。 |
| 订单与购票         | 用户选定航班实例、舱位、票价类型和乘机人后，可以创建订单。系统在下单时需要校验航班实例是否可订、库存是否充足、乘机人是否重复购票，并记录下单时刻的成交价。订单创建后进入待支付状态，支付成功后变为已支付；若超时未支付，系统取消订单并释放库存。 |
| 退票与改签         | 用户可以对本人名下的有效客票申请退票或改签。系统需要校验用户身份、客票状态和航班状态。退票时根据距离起飞时间计算手续费并回补库存；改签时作废原客票，扣减新航班实例库存，生成新客票，并记录手续费和票价差额。 |
| 中转与临近机场推荐 | 系统需要在直飞航班之外支持单次中转和临近机场推荐。中转方案由两段航班组成，两段之间的衔接时间限制为 120 至 360 分钟，且两段都必须有可售舱位。临近机场方案基于 `city_near_apt` 的距离关系扩展出发或到达机场范围。 |

### 1.5 核心业务规则

系统的核心业务规则主要包括状态流转、库存控制、退改费用计算和航班推荐约束。这些规则直接影响订单、客票、航班实例和库存数据的一致性。

| 规则类别         | 具体规则                                                     |
| ---------------- | ------------------------------------------------------------ |
| 订单状态规则     | 订单创建后默认为“待支付”。用户支付成功后，订单变为“已支付”。如果订单超时未支付或用户主动取消，订单变为“已取消”，并释放已占用库存。退票后，系统根据订单内剩余有效客票数量，将订单更新为“部分退款”或“已完成退款”。航班完成后，订单可进入“已完成”状态。 |
| 客票状态规则     | 客票创建后默认为“有效”。有效客票可以正常乘机，也可以在符合条件时申请退票或改签。退票后，客票状态变为“已退”；改签后，原客票状态变为“已改签作废”，系统生成新的有效客票；乘机完成后，客票状态变为“已使用”。已退、已改签作废和已使用的客票不能再次退改。 |
| 航班实例状态规则 | 航班实例包括“计划”“可订”“已起飞”“已到达”“已取消”等状态。只有“可订”状态的航班实例可以被用户购买。系统通过定时任务按计划起降时间自动把实例流转为“已起飞”“已到达”；退改流程主要按客票状态、订单状态和计划起飞时间校验。 |
| 库存规则         | 系统同时维护舱位定价层面的可售座位数和航班实例层面的舱位剩余座位数汇总。下单时扣减对应库存；退票、改签旧票释放和订单超时取消时回补库存；改签生成新票时扣减新航班实例库存。库存不能出现负数，并发购票时不能发生超卖。 |
| 退改签费率规则   | 退票和改签手续费按照操作时间距离航班计划起飞时间分档计算，手续费基数为客票成交价，而不是当前挂牌价。距起飞时间越近，手续费比例越高；航班已起飞后不可退改。 |
| 中转规则         | 中转推荐只支持一次中转，不支持两次及以上中转。第一段航班的到达机场必须等于第二段航班的起飞机场，中转衔接时间应在 2 小时至 6 小时之间，两段航班都需要有余票，且不要求属于同一航空公司。 |
| 临近机场规则     | 系统通过城市临近机场关系维护城市与机场之间的可替代关系。距离为 0 的记录表示该机场属于该城市；距离大于 0 的记录表示该机场可作为该城市的临近机场。航班查询时，系统可以基于该关系扩展出发或到达机场范围。 |

退改签手续费率如下表所示：

| 距起飞时间 | 退票手续费率 | 改签手续费率 |
| ---------- | ------------ | ------------ |
| ≥ 30 天    | 0%           | 0%           |
| 7 - 30 天  | 20%          | 20%          |
| 3 - 7 天   | 40%          | 40%          |
| 1 - 3 天   | 60%          | 50%          |
| < 1 天     | 80%          | 60%          |
| 已起飞     | 不可操作     | 不可操作     |

### 1.6 数据需求分析

为支撑上述业务流程，系统需要存储航班基础数据、用户与乘机人数据、订单与客票数据、退改记录数据和管理员数据。不同类型的数据分别服务于航班查询、购票、退改签、后台维护和运营核对等场景。

| 数据类别         | 数据内容                                                     | 用途                                                       |
| ---------------- | ------------------------------------------------------------ | ---------------------------------------------------------- |
| 航班基础数据     | 城市、机场、临近机场、航空公司、机型、航班计划、航班飞行日、航班经停、航班实例、舱位定价 | 支撑航班查询、基础数据维护、库存管理和票价管理             |
| 用户与乘机人数据 | 用户账号、手机号、密码哈希、昵称，乘机人的证件号、姓名和出生日期，以及用户-乘机人绑定关系 | 支撑用户登录、实名购票、常用乘机人管理、多人同行购票和订单归属判断 |
| 订单与客票数据   | 订单号、用户、订单金额、订单状态、创建时间、客票号、乘机人、航班实例、舱位、票价类型、成交价和客票状态 | 记录用户购票行为，支撑订单查询、支付、退票、改签和状态追踪 |
| 退改记录数据     | 退改记录编号、原客票号、操作类型、手续费、新客票号、票价差额和操作时间 | 记录退票和改签历史，便于用户查询和管理员核对               |
| 管理员数据       | 管理员账号、密码哈希和管理员姓名                             | 支撑管理端登录和后台权限控制                               |

### 1.7 非功能需求

除功能需求外，系统还需要满足数据一致性、并发控制、安全性、性能、可维护性和可追踪性等非功能需求。这些需求主要用于保证系统在多用户、多订单和频繁库存变化场景下仍能稳定运行。

| 非功能需求 | 具体说明                                                     |
| ---------- | ------------------------------------------------------------ |
| 数据一致性 | 下单、支付、取消、退票和改签都可能同时影响订单、客票和库存数据。系统需要将相关操作作为完整事务处理，避免出现订单创建成功但库存未扣减、客票已退但库存未回补等不一致情况。 |
| 并发控制   | 在多个用户同时购买同一航班余票时，系统需要避免超卖。对于仅剩少量余票的航班实例，同时发起多个下单请求时，成功订单数不能超过实际可售库存。 |
| 安全性     | 用户和管理员密码不得明文存储；普通用户只能查看和操作自己的订单与客票；管理员接口需要进行身份校验；数据库查询应避免直接拼接用户输入；登录状态需要设置过期机制。 |
| 性能需求   | 系统应能在课程项目规模的数据量下完成查询和下单操作。直飞查询依赖 `idx_flight_route`、`idx_instance_date_status` 和 `v_flight_search`；中转查询通过候选航班自连接、时间窗口和可售舱位过滤控制组合规模；超时订单扫描依赖 `(status, created_at)` 索引。 |
| 可维护性   | 系统应将用户、航班、订单、客票、退改签等业务数据分开管理，避免不同业务逻辑混杂。基础数据维护、购票流程和退改签流程应具有清晰边界，便于后续修改和扩展。 |
| 可追踪性   | 系统需要记录关键业务操作结果，包括订单创建、支付、取消、退票和改签。退改签操作不仅要更新当前状态，还要保留操作记录，方便用户查询和管理员核对。 |

### 1.7 数据规模与覆盖范围

为提高系统演示的真实性，本项目整理并导入了较大规模的基础数据。基础数据覆盖全国主要城市、机场、航空公司、机型和航线计划，其中包括 328 个城市、180 个机场、15 家航空公司、19 种机型、10141 条航班计划、58247 条航班飞行日记录，以及 1222 条城市-临近机场关系。航班实例和舱位定价则由程序根据航班计划、飞行日和预售周期自动生成。

相比只录入少量样例数据，本项目的数据规模更接近真实票务查询场景，能够支撑直飞搜索、中转自连接查询、临近机场扩展查询、库存扣减和订单超时释放等功能的完整演示。

### 3.3 跨表完整性约束

| 约束描述 | 约束位置                 |
| :--- | ---- |
| 同一乘客在同一航班实例上仅能有 1 张有效客票                  | 下单时 SELECT 校验       |

### 4.1 用户与权限模块

#### U1 用户注册

| 项目 | 说明 |
|------|------|
| 输入 | 手机号（11 位）、密码（6-32 位）、昵称（1-64 字） |
| 处理逻辑 | 校验手机号格式 → 查重（`user` 表 UNIQUE(phone)） → bcrypt 哈希密码 → INSERT `user` |
| 异常     | `INVALID_PHONE_FORMAT`（格式错误）、`PHONE_ALREADY_EXISTS`（重复） |

#### U2 用户登录 / U3 管理员登录

| 项目 | 说明 |
|------|------|
| 输入 | 手机号（或 admin_id）+ 密码 |
| 处理逻辑 | 查 `user`（或 `admin`）表 → bcrypt 验证密码 → 签发 JWT |
| 异常     | `AUTHENTICATION_FAILED`（手机号不存在或密码错误）            |
| 安全设计 | 密码哈希不进日志；JWT 通过 httpOnly cookie 传递；管理员账号由初始化脚本写入，不开放前台注册 |

#### U4 修改个人信息 / U5 乘机人管理 / U6 退出登录

| 功能 | 处理逻辑 |
|------|---------|
| 修改信息 | PATCH `user` 表（name / phone），修改密码需验证旧密码 |
| 乘机人管理 | `passenger` 表的 增删改查，乘机人与用户通过 `user_passenger` 显式绑定 |
| 退出 | 清除 `access_token` cookie |

### 4.2 基础数据维护模块

#### A1 城市表 / A2 机场表 / A3 航司表 / A4 机型表

| 功能 | 关键处理逻辑 |
|------|-------------|
| 城市 增删改查 | 单表 `city`，删除时若被 `airport.city_name` 或 `city_near_apt` 引用则拒绝 |
| 机场 增删改查 | 新增：事务内双写 `airport` + `city_near_apt(city_name, iata_code, 0)`。修改 `city_name`：事务内同步更新旧/新 `city_near_apt` 的 distance=0 记录。删除：若被 `flight` 引用则拒绝 |
| 航司 增删改查 | 单表 `airline`，删除时若被 `flight.airline_code` 引用则拒绝 |
| 机型 增删改查 | 单表 `aircraft_type`，删除时若被 `flight.aircraft_model` 引用则拒绝 |

#### A5 航班表

| 项目 | 说明 |
|------|------|
| 输入 | `flight_no`、起降时刻、燃油基建费、基础裸票价、起降机场（含航站楼）、航司、机型、`weekdays[]`、`stopovers[]` |
| 处理逻辑 | 校验起降不同机场、经停≠起降， INSERT `flight` + 批量 INSERT `flight_weekday` + `flight_stopover` |
| 约束 | `flight_weekday` 和 `flight_stopover` 随 `flight` 级联删除，但若已有 `flight_instance` 引用则拒绝删除航班 |

#### A6 航班实例 / A7 舱位定价

| 功能 | 处理逻辑 |
|------|---------|
| 创建单个实例 | 校验 flight_date 落在 flight_weekday 内，按 `aircraft_type` 座位数初始化 `economy_left` / `first_left`，复制航班计划的燃油基建费，并按 `base_price` 生成默认舱位定价 → INSERT `flight_instance`（status='计划'） |
| 批量生成 | 遍历日期区间，对每个落在飞行日内的日期创建实例。幂等性由 `UNIQUE(flight_no, flight_date)` 保证 |
| 状态变更 | 管理员可修改实例状态；设为“已取消”后前台不可继续售票，相关客票仍通过退改流程处理 |
| 舱位定价 | 按 `(instance_id, cabin_class, fare_type)` 三元组维护 `price` 和 `available_seats`。批量设置时事务内同步刷新 `flight_instance.economy_left / first_left` 汇总值 |

### 4.3 航班查询模块

#### F1 三类候选合并搜索

| 项目 | 说明 |
|------|------|
| 输入 | 出发城市、到达城市、出行日期 |
| 处理逻辑 | 按请求参数分别查询三类候选：①直飞：通过 `v_flight_search` 连接 `city_near_apt(distance=0)` 匹配出发/到达城市自有机场；②中转：用候选航班自连接，约束第一段到达机场=第二段起飞机场，衔接时间 ∈ [120min, 360min]，允许第二段跨到次日，且两段都有可售舱位；③临近机场：使用 `city_near_apt(distance>0)` 扩展出发或到达机场。合并搜索中，中转和临近方案仅保留价格低于最贵直飞代表价的结果；无直飞时不设价格阈值。 |

#### F2 筛选 / F3 排序 / F4 详情

| 功能 | 处理逻辑 |
|------|---------|
| F2 筛选 | 在三路结果上应用：航司（WHERE airline_code=）、舱位（JOIN cabin_price WHERE cabin_class= 且 available_seats>0）、起飞时间段（WHERE scheduled_departure BETWEEN）、是否经停（JOIN flight_stopover EXISTS/ NOT EXISTS） |
| F3 排序 | 前端传 `sort.field`（price/duration/departure）+ `sort.order`（asc/desc），后端在 SQL 中 `ORDER BY` |
| F4 详情 | 返回航班完整信息 + `cabin_prices[]`（各档位价格与剩余座位），含经停信息 |

### 4.4 订单与购票模块

#### O1/O2 创建订单（下单事务）

| 步骤 | 操作 | SQL/校验 |
|------|------|---------|
| 1 | 校验实例状态 | `instance.status = '可订'` |
| 2 | 校验乘机人去重 | SELECT ticket WHERE passenger_id= 且 instance_id= 且 status='有效' |
| 3 | 锁定舱位定价行 | `SELECT ... FOR UPDATE` 锁定 `cabin_price` 行，校验 `available_seats >= count` |
| 4 | 扣减精细库存 | `UPDATE cabin_price SET available_seats -= count` |
| 5 | 同步汇总库存 | `UPDATE flight_instance SET economy_left -= count`（或 first_left） |
| 6 | 计算金额 | `actual_price = cabin_price.price + flight_instance.fuel_infra_fee`（下单时刻快照）；`ticket.fuel_infra_fee` 单独保存燃油基建费快照；`total_amount = actual_price × 乘机人数 × 航段数` |
| 7 | 创建订单 | INSERT `aptorder`（status='待支付'，`created_at= NOW()`） |
| 8 | 创建客票 | 每位乘机人在每个航段 INSERT 一条 `ticket`（status='有效'，`actual_price` 与 `fuel_infra_fee` 均为快照值） |

#### O3 模拟支付 / O4 超时释放 / O5-O6 订单查询

| 功能 | 处理逻辑 |
|------|---------|
| O3 支付 | 校验 status='待支付' → UPDATE `aptorder.status='已支付'`。异常：`ORDER_NOT_PAYABLE` |
| O4 超时释放 | 定时任务每分钟扫描 `status='待支付' AND created_at < NOW() - 15min` → 事务内：取消订单 → 所有客票→已退 → 回补 cabin_price 库存 → 回补 flight_instance 汇总库存 |
| O5 订单列表 | SELECT `aptorder` WHERE user_id= 按 created_at DESC 分页，可 `?status=` 筛选 |
| O6 订单详情 | JOIN `aptorder` + `ticket` + `passenger` + `flight_instance`，含每张客票的完整信息 |

### 4.5 退改签模块

#### R1 退票

| 步骤 | 操作 | 说明 |
|------|------|------|
| 1 | 校验客票状态 | `ticket.status = '有效'`，否则 `TICKET_NOT_REFUNDABLE` |
| 2 | 校验起飞时间 | 根据航班实例日期和起飞时刻计算计划起飞时间；已起飞不可退票 |
| 3 | 计算手续费 | 按距起飞天数查 `REFUND_FEE_TIERS`（见 §1.5 费率表），基数 = `ticket.actual_price` |
| 4 | 更新客票 | `ticket.status = '已退'` |
| 5 | 回补库存 | `cabin_price.available_seats += 1` + `flight_instance` 汇总 +1 |
| 6 | 写退改记录 | INSERT `refund_change`（op_type='退票', fee, new_ticket_no=NULL, price_diff=0） |
| 7 | 订单状态联动 | 全退→'已完成退款'，部分退→'部分退款' |

#### R2 改签

| 步骤 | 操作 | 说明 |
|------|------|------|
| 1 | 校验旧票状态 | `ticket.status = '有效'` |
| 2 | 校验新实例 | 新实例 status='可订'、余票充足 |
| 3 | 校验目标不同 | 目标航班实例、舱位、票价类型不能与原票完全相同，否则 `SAME_TICKET_NOT_ALLOWED` |
| 4 | 计算费用 | 手续费（同退票费率表）+ 新票价差额（`new_actual_price - old_actual_price`） |
| 5 | 作废旧票 | `old_ticket.status = '已改签作废'` |
| 6 | 回补旧实例库存 | 旧 `cabin_price` +1，旧 `flight_instance` 汇总 +1 |
| 7 | 扣减新实例库存 | 新 `cabin_price` -1，新 `flight_instance` 汇总 -1 |
| 8 | 生成新票 | INSERT `ticket`（status='有效'，`order_no` 仍指原订单） |
| 9 | 写退改记录 | INSERT `refund_change`（op_type='改签', fee, new_ticket_no=新票号, price_diff） |

### 4.6 中转联程推荐模块

#### C1 直飞匹配

查询逻辑：出发城市 → `city_near_apt`（distance=0）获取该城市自有机场 → 以此机场作为 `dep_airport_code` 查 `v_flight_search`，同理获取到达城市自有机场作为 `arr_airport_code`。

#### C2 中转匹配

核心算法：`v_flight_search` 自连接。

| 约束项 | 值 |
|--------|-----|
| 衔接机场 | leg1.arr_airport = leg2.dep_airport |
| 衔接时间 | 120 min ≤ 衔接 ≤ 360 min |
| 日期范围 | leg2.flight_date ∈ [date, date+1]（允许跨日中转） |
| 库存要求 | leg1.economy_left>0 AND leg2.economy_left>0 |
| 航司限制 | 不限（允许跨航司） |
| 中转次数 | 仅单次（不递归） |

#### C3 临近机场替代

查询 `city_near_apt WHERE city_name=目标城市 AND distance>0 AND distance≤300` ，以临近机场的 IATA 码替代原出发/到达机场，重新查 `v_flight_search`。

## 第六章 系统实现

### 6.1 系统架构设计

系统采用"领域驱动 + 跨领域编排"的分层架构，代码组织分为三个层级，依赖方向严格自上而下：

```
┌──────────────────────────────────────────────────────────┐
│  workflows/   跨领域编排层（Application Services）        │
│  - booking/   下单流程：协调 flight + order + ticket     │
│  - refund/    退改流程：协调 ticket + flight + order     │
│  - search/    航班搜索：协调 flight + city_near_apt      │
│  ↓ 可调用 domains 和 core                                │
├──────────────────────────────────────────────────────────┤
│  domains/     业务领域层（Domain Services）               │
│  - city/ airline/ flight/ user/ order/ ticket/ admin/    │
│  ↓ 各领域包之间互相不调用，只能调用 core                 │
├──────────────────────────────────────────────────────────┤
│  core/        基础设施层（Infrastructure）                │
│  - database / security / exceptions / scheduler          │
│  - id_generator / constants / logging                   │
│  ↓ 不调用上层，只被上层调用                              │
└──────────────────────────────────────────────────────────┘
```

### 6.2 领域内部的四层结构

每个 `domains/<name>/` 包内部仍然分四层：

```
router.py      ↓ HTTP 入口，FastAPI 装饰器在这里
   ↓
service.py     ↓ 业务逻辑，事务边界，业务规则校验
   ↓
repository.py  ↓ 数据访问，只关心"取/存数据"，不写业务规则
   ↓
models.py      ↓ SQLAlchemy ORM 实体类（对应数据库表）
schemas.py     旁挂 Pydantic DTO（请求/响应模型，与 ORM 解耦）
```

**各层职责：**

| 层 | 职责 | 不该做的事 |
|----|------|-----------|
| `router.py` | 接收 HTTP、解析参数、调用 service、返回响应 | 写业务逻辑、直接操作 DB |
| `service.py` | 业务规则、事务边界、调用 repository | 直接调用其他 domain 的 repository、写 SQL |
| `repository.py` | SQL/ORM 查询封装、参数化查询 | 写业务规则、调用其他 domain |
| `models.py` | ORM 实体（与 SCHEMA 一一对应） | 包含业务方法 |
| `schemas.py` | Pydantic DTO，请求体与响应体 | 与 ORM 类混用 |

### 6.3 防超卖

使用 `with_for_update()` 对 `cabin_price` 行加悲观锁，校验库存 → 扣减 `available_seats` → 同步更新 `flight_instance.economy_left/first_left`。下单、主动取消、超时释放、退票和改签都通过 `FlightService.deduct_seat()` / `restore_seat()` 维护精细库存与汇总库存，避免只改一边造成数据不一致。

### 6.4 复杂查询与视图复用

数据库中建立 `v_flight_search` 视图，把航班实例、航班计划、机场和航司的常用 JOIN 结果预先组织好。直飞查询在该视图上连接 `city_near_apt(distance=0)`，中转查询使用候选航班自连接并通过 `TIMESTAMPDIFF` 限制 120 至 360 分钟的衔接窗口，临近机场查询则使用 `city_near_apt(distance>0)` 扩展出发或到达机场。复杂查询使用 SQLAlchemy `text()` 编写原生 SQL，参数通过绑定变量传入。

### 6.5 票价与费用快照

航班计划表保存 `base_price` 和默认燃油基建费；生成航班实例时，实例复制当天的 `fuel_infra_fee`，并按默认定价规则生成 `cabin_price`。用户下单时，客票同时保存 `actual_price` 和 `fuel_infra_fee` 快照，因此后续管理员调整票价或燃油基建费不会影响历史订单、退票手续费和订单详情中的金额拆分。

### 6.6 定时任务

系统使用 APScheduler 注册三个后台任务：`expire_orders_job` 定期扫描超时待支付订单并回补库存；`generate_instances_daily` 每天生成提前预售窗口末端那一天的航班实例；`sync_flight_status_job` 定期根据当前时间把航班实例自动流转为“已起飞”或“已到达”。这些任务都复用 service 层逻辑和统一事务封装。

### 6.7 航班调整提示

`flight_instance` 记录 `adjusted_at` 以及起飞时间、到达时间、起飞机场、到达机场四类单独调整时间。订单详情查询会比较这些调整时间与订单创建时间，若调整发生在下单之后，就向前端返回“起飞时间已调整”“降落时间已调整”“起飞机场已调整”“降落机场已调整”等标签，方便用户识别购票后的航班变更。

### 6.8 前端实现

前端采用 Vue 3 + TypeScript + Element Plus。用户端首页直接提供航班搜索入口，搜索结果把直飞、中转和临近机场候选合并展示，并支持筛选、排序和低余票提示；订单详情展示机票价与燃油基建费拆分、客票状态和航班调整提示；支付页提供订单倒计时；退票和改签页先试算手续费、退款额或补差额，再提交事务操作。管理端以表格为主维护城市、机场、航司、机型、航班、航班实例和舱位定价。
